This section describes the selected architecture for designing an Ingest Tool that operates based on configuration and versioned ingest flow templates. The objective is to align the ingestion process with Data Mesh principles by assigning ownership of configurations, deployments, and operational responsibility to individual Business Unit squads.

The Platform Squad provides a Templates Library containing versioned ingest flow templates for different processing patterns, such as Full, Delta, or kafka ingestion. Each Business Unit squad selects the appropriate template and deploys a copy of it, together with the corresponding configuration, into its own Git repository.

All configurations, selected templates, and deployment artifacts are version-controlled in Git and delivered through standard CI/CD pipelines. This ensures that every change is traceable, reviewable, reproducible, and consistently promoted across environments.

The behavior of each ingestion flow is determined by the selected template type and version together with the configurations owned by the corresponding Business Unit squad. The selected template contains the complete ingestion implementation, while squad-specific behavior is controlled through the referenced configuration files.

Principles

  • Configurations are fully owned by the corresponding Business Unit squad.
  • All configuration, template, and deployment artifacts used by an ingest flow are versioned and maintained in the squad's Git repository.
  • The Platform Squad provides versioned ingest flow templates for supported ingestion patterns.
  • Each Business Unit squad selects an appropriate template and deploys it together with the corresponding configuration.
  • Squads define what data should be exported and how the export should behave, while the ingestion implementation remains standardized within each supported template type and version.
  • Each squad owns the deployment, operation, and lifecycle of its resulting ingest flows.
  • Squads decide when to upgrade to a newer supported template version, except when a mandatory security or critical defect fix is required.

Templates Library

The Templates Library contains versioned ingest flow templates for different processing patterns and execution technologies.

Templates may differ substantially in their functionality and implementation. For example, Full and Delta ingestion use separate templates because they implement different processing logic. Kafka-based ingestion may also use a separate template where a different execution technology is required.

Each template contains the complete implementation required to execute the corresponding ingestion pattern. Template customization is intentionally limited to supported parameters, primarily the reference to the input Export Configuration YAML file.

A Business Unit squad selects a template and a specific template version from the Templates Library. A copy of the selected template is stored and deployed from the squad's own Git repository together with the corresponding configuration files.

Template Lifecycle

  • The Platform Squad develops, tests, documents, and publishes new template versions.
  • Business Unit squads select the appropriate template type and version for their ingest flows.
  • Template upgrades are performed through the standard pull request and CI/CD process in the squad repository.
  • During pull request validation, the configuration is validated against the selected template type and version.
  • The Platform Squad defines which template versions are supported, deprecated, or no longer supported.
  • Security patches and critical defect fixes are distributed as new template versions together with an upgrade request or mandatory upgrade deadline.
  • An inventory of deployed ingest flows and their template versions is maintained to support lifecycle management and security patching.

Configuration Components

1. Object Schema

Defines what will be stored in the generated Parquet dataset.

The schema describes the structure of the exported data, including:

  • Dataset name and version
  • Column definitions
  • Physical and logical data types
  • Source object reference

The schema is expected to follow a standardized format to ensure consistent validation and interoperability across the platform.

Lifecycle

  • During migration, schemas can be generated from existing XML or JSON definitions.
  • For new developments, schemas may be generated from source databases or Bronze-layer datasets.
  • Schema changes are typically driven by source-system DDL changes.

Example

  version: "1.0"
name: crm/customer
source: CRM.CUSTOMER

columns:
  - name: CUSTOMER_ID
    physical_type: INT64   # Data storage format in Parquet
    logical_type: INTEGER  # Data format in the source system

  - name: CUSTOMER_NAME
    physical_type: BYTE_ARRAY
    logical_type: STRING

  - name: CUSTOMER_EMAIL
    physical_type: BYTE_ARRAY
    logical_type: STRING

  - name: UPDATE_TS
    physical_type: INT64
    logical_type: TIMESTAMP

2. Export Configuration

Defines where and how data should be exported.

The export configuration contains operational settings required by the selected ingest flow template.

Typical Configuration Elements

  • Source connection reference
  • Source system type
  • Export mode identifying the expected processing pattern
  • Watermark column definition
  • Schema validation strategy
  • Export destination
  • Activation status

Supported Capabilities

  • Connection details stored securely in a vault
  • Full or Delta extraction using the corresponding ingest flow template
  • Incremental loading using a watermark column
  • Schema validation modes such as strict or breaking-changes
  • Multiple export destinations

The load_mode value does not dynamically select or change the implementation of the ingest flow. It is used to validate that the Export Configuration corresponds to the selected template. For example, a configuration with load_mode: full must be deployed with a Full ingest flow template.

Compatibility between the Export Configuration and the selected template type and version is validated as part of the pull request CI/CD process.

Example

  export_id: CRM_EXPORTS

connection_id: CRM_DB
source_type: oracle

load_mode: full
validate_schema: breaking-changes
active: true

run_condition_file: run_condition.txt

exports:
  - source_object: CRM.CUSTOMER
    schema_ref: crm-customer
    watermark_column: UPDATE_TS

    export_location:
      type: s3
      path: crm/customer

  - source_object: CRM.CUSTOMER_CONTACTS
    schema_ref: crm-customer-contacts

    export_location:
      type: filesystem
      path: crm/customer-contacts

3. Run Conditions

Defines whether the ingestion flow is allowed to start.

Run conditions are implemented as SQL queries executed before the export process begins.

Typical Use Cases

  • Verifying that upstream processing has completed successfully.
  • Checking whether source data is available.
  • Implementing dependencies on enterprise scheduling processes.

Only a subset of ingestion flows requires run conditions.

Expected Result

The SQL query should return a single record representing the execution decision.

  • Boolean
  • Date
  • Timestamp

For consistency and simplicity, returning a Boolean value is the preferred approach.

Example

  SELECT
    CASE
        WHEN COUNT(*) > 0 THEN TRUE
        ELSE FALSE
    END AS can_run
FROM CONTROL_TABLE
WHERE BUSINESS_DATE = CURRENT_DATE;

Validation

Changes to templates and configuration artifacts are validated through the standard pull request process before deployment.

The validation process should verify at least the following:

  • The Object Schema and Export Configuration use a supported format.
  • All required configuration attributes are present.
  • All schema_ref values reference existing and valid Object Schema definitions.
  • The configured load_mode corresponds to the selected ingest flow template.
  • The configuration is compatible with the selected template version.
  • The selected template version is supported by the Platform Squad.
  • The template has not been modified outside the explicitly supported customization parameters.

Template Versioning and Inventory

Every deployed ingest flow must be associated with a specific template type and version. This information must be traceable from the squad repository and available in a central inventory.

The inventory should provide an overview of:

  • Deployed ingest flows
  • Owning Business Unit squads
  • Selected template types
  • Deployed template versions
  • Support status of each template version
  • Required or recommended upgrades

The inventory enables the Platform Squad to identify flows affected by security vulnerabilities, critical defects, compatibility changes, or end-of-support decisions.

Upgrade Model

Business Unit squads normally decide when to upgrade their ingest flows to a newer supported template version. An upgrade is performed by replacing the existing template with the selected newer version in the squad repository and delivering the change through the standard pull request and CI/CD process.

The Platform Squad communicates newly available versions, security patches, defect fixes, compatibility requirements, and end-of-support dates. Security vulnerabilities or defects that may cause data corruption, data loss, or significant operational risk may require a mandatory upgrade within a defined deadline.

Multiple supported template versions may coexist in production. The Platform Squad defines the support lifecycle and determines which versions are supported, deprecated, or no longer supported.

Operational Considerations

A single ingest flow may process multiple source objects defined in one Export Configuration. Although the objects share the same orchestration cycle, the processing status of each object should remain observable.

Monitoring and logging should provide object-level information, including:

  • Processing status
  • Start and completion time
  • Number of exported records
  • Validation result
  • Failure details
  • Retry information


Ownership Model

Artifact Owner Responsibility
Templates Library Platform Squad Development, testing, documentation, release, versioning, security patching, and lifecycle management of ingest flow templates
Object Schema Business Squad Definition and maintenance of the exported data structure
Export Configuration Business Squad Definition and maintenance of export behavior
Run Conditions Business Squad Definition and maintenance of execution prerequisites
Selected Template Copy Business Squad Selection, version control, supported configuration, and upgrade of the template deployed in the squad repository
Deployed Ingest Flow Business Squad Deployment, monitoring, operation, incident resolution, and lifecycle management of the resulting ingest flow
Template Version Inventory Platform Squad Central overview of deployed flows, owners, template versions, support status, and required upgrades

Summary

This approach aligns with Data Mesh principles by assigning ownership of configuration, deployment, and operation to Business squads while keeping template development, standardization, versioning, and lifecycle management centralized within the Platform Squad.

The Platform Squad provides versioned templates for different ingestion patterns, such as Full, Delta, or Spark-based ingestion. Each Business Unit squad selects an appropriate template, deploys a copy of it together with the corresponding YAML configuration in its own Git repository, and owns the resulting ingest flow.

Squads control the timing of standard template upgrades, while central inventory, pull request validation, security notifications, and template support policies provide the governance required to operate multiple template types and versions safely.
