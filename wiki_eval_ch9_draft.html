9. Evaluation Summary and Recommendation

Evaluation Summary

Several alternatives for generating Parquet datasets from source systems were evaluated across the following dimensions:

  • Development and adoption complexity
  • Implementation and migration effort
  • Functional capabilities
  • Data Mesh alignment
  • Target architecture alignment
  • Security and governance
  • Operational capabilities
  • Proof of Concept results

Following the initial assessment, the Preparing Extracts at Source (PNJ) and Adoki Offloader alternatives were excluded from further consideration. These options introduced significant disadvantages in terms of operational complexity, long-term sustainability, contractual or platform dependencies, and overall cost.

Meltano was excluded after the Proof of Concept. The export of 80 million rows took approximately 4 hours, compared with 5 to 15 minutes for the other alternatives.

The final comparison therefore focused on the following alternatives:

  • Airflow + Python (AirPy)
  • Apache MiNiFi (Java agent)
  • Apache NiFi
  • Informatica PowerCenter (Infa)

MiNiFi was evaluated on the assumption that it runs in Kubernetes (K8s). Each ingest flow is started per run as a pod from the SOGE on-premises Airflow (KubernetesPodOperator). The Parquet files and the related metadata (watermark) are stored on the internal S3 storage, so the pod itself is stateless. The flow definition and the YAML configuration are versioned in the Git repository of the owning squad, in line with the Versioned Template Library (B2).

In the scoring tables, AirPy and MiNiFi achieved clearly better results than NiFi, Informatica PowerCenter and Meltano. MiNiFi achieved the best result in the Functional Capabilities category, while AirPy achieved the best results in the Data Mesh alignment, security and operational categories.

Airflow + Python (AirPy)

AirPy achieved strong results across most evaluation categories and demonstrated the best runtime performance during the Proof of Concept.

Key strengths:

  • No licensing costs
  • Reuse of the existing Airflow platform and operational ecosystem
  • Strong CI/CD and Git integration
  • Simple automation and generation of new extraction flows using templates
  • Good alignment with the target cloud architecture
  • Strong operational capabilities, including monitoring, retry mechanisms, alerting, autorestarts, and SLA handling
  • CyberArk integration and password rotation validated in the Proof of Concept
  • Good alignment with Data Mesh principles and squad ownership
  • Ability to reuse existing Python libraries (PyArrow, pyodbc, pandas, connectors) for database access and Parquet generation, reducing the need for custom development and leveraging existing internal expertise.

Key limitations:

  • A custom extraction framework must be developed and maintained in Airflow, including incremental loading, watermark management, schema validation and Parquet generation.
  • The solution depends on maintaining sufficient internal expertise and ownership of this framework.
  • Python-based processing may not provide sufficient performance for all future high-volume workloads.
  • Kafka and Elasticsearch would have to be handled by another tool (for example NiFi), which results in two tools instead of one.
  • The preferred solution would integrate with the SOGE on-premises Airflow platform through KubernetesPodOperator to execute Python scripts in the KB Kubernetes environment, eliminating the need for a dedicated Airflow runtime in KB. It introduces the same Kubernetes infrastructure and expertise requirements as the MiNiFi approach. The alternative would be to deploy a standalone Airflow instance in the KB on-premises environment, which would require maintaining two separate Airflow instances and their operational integration.

Apache NiFi

NiFi demonstrated strong technical capabilities, in particular for streaming workloads.

Key strengths:

  • Native support for streaming workloads and Kafka integration
  • Native support for incremental processing
  • No licensing costs

Key limitations:

  • More complex CI/CD integration and environment promotion
  • More challenging automated flow generation
  • More complex governance, version management, and object lifecycle
  • Complicated integration with Airflow orchestration
  • Higher adoption and training effort across squads
  • More complex integration with CyberArk and password rotation

NiFi is technically capable, but it introduces additional operational, integration, and governance complexity that the MiNiFi deployment model (a flow file in Git, a pod started per run from Airflow) avoids while using the same processors.

Informatica PowerCenter

PowerCenter remains a mature and proven enterprise platform with significant internal adoption, existing expertise, and established operational processes.

Key strengths:

  • Existing know-how and operational experience within KB
  • Established integration with existing operational and security processes
  • Native and mature Teradata connectivity
  • Stable and proven operational model
  • Low adoption risk for existing Informatica teams
  • Natural separation of configuration and implementation ownership

Key limitations:

  • Additional licensing and lifecycle costs
  • Slower than AirPy in the Proof of Concept
  • Reduced flexibility for automated flow generation at scale
  • Limited support for Parquet generation without additional transformations
  • Limited long-term strategic outlook due to the product lifecycle
  • Lower alignment with the target cloud architecture

PowerCenter presents the lowest transformation and adoption risk, but it also provides the least strategic value for the future target architecture and retains dependency on a licensed platform with a limited lifecycle.

Key Findings

Apache MiNiFi (Java agent)

The MiNiFi Java agent runs the same processors as Apache NiFi (database, Kafka, Elasticsearch, Parquet and S3 processors) in a lightweight form without a user interface. Since NiFi 2, MiNiFi Java is part of the NiFi release line. The flow is a definition file kept in Git, which suits the template-based ownership model.

Key strengths:

  • One tool covers all source types, including Kafka and Elasticsearch. The alternative of using AirPy for batch sources and NiFi for Kafka and Elasticsearch would mean two tools, two skill sets, two CI/CD pipelines and two operating models.
  • Ready-made processors are used instead of a custom-built framework. This applies to database extraction, Parquet export and import, Kafka, Elasticsearch, S3 and incremental loading.
  • Best result among the alternatives in the Functional Capabilities category.
  • Strong CI/CD and Git integration: the flow definition and the YAML configuration are stored in Git, validated in pull requests, and the same image is promoted through the environments with environment-specific configuration.
  • Independent flows: each run is an isolated pod in the namespace of the owning squad, with Kubernetes RBAC and Airflow retries.
  • The incremental logic and watermark management are implemented once in the template. For operational incident recovery, the watermark value should be configurable to any arbitrary value, enabling quick recovery without requiring manual intervention on the underlying storage (such as S3).
  • No licensing costs. The core components are maintained by the Apache NiFi community.
  • Good alignment with the target architecture (Kubernetes, Airflow, S3).
  • The Airflow-Kubernetes integration (KubernetesPodOperator) provides a reusable capability that delivers value beyond the ingest solution, supporting orchestration across the migration and other (Airflow On Prem SOGE<->KB) platform use cases. This integration is supported by KB security.

Key limitations:

  • Platform Squad must build the know-how of NiFi and MiNiFi. Similarly, Kubernetes expertise is present in the Platform Squad, but not at a sufficient level to ensure long-term stability.
  • Cross-environment network connectivity must be established between the SOGE on-premises Airflow and the KB Kubernetes environment for KubernetesPodOperator to function. However, this is a standard REST API-based integration pattern and should be feasible to implement and support operationally.
  • MiNiFi Java is a continuously running agent and no run-once mode is documented. A wrapper (or the NiFi Stateless runtime) is needed so that the pod finishes after processing and returns an exit code to Airflow.
  • CyberArk and password rotation have not yet been validated. The design assumes that Airflow retrieves the credentials for each run and passes them to the pod.
  • Weaker documentation and lower adoption in the industry than the alternatives, because MiNiFi is used mainly as an edge data collection agent.
  • The runtime in the Proof of Concept was approximately 10 minutes, compared with approximately 5 minutes for AirPy.

Recommendation

Recommended option: Apache MiNiFi (Java agent), run as a pod in Kubernetes and started per load from the SOGE on-premises Airflow

The recommendation is primarily driven by:

  • One tool for all source types, including Kafka and Elasticsearch, instead of a combination of AirPy for batch sources and NiFi for streaming sources
  • Ready-made components instead of a custom-developed framework in Airflow, which is in line with the requirement of the migration project to reuse existing solutions
  • The best result in the Functional Capabilities category
  • Strong CI/CD and Git integration, with the flow and the configuration stored in Git and the same image promoted across environments
  • Independent flows with clear squad ownership and Kubernetes RBAC
  • No licensing costs
  • Good alignment with the target architecture (Kubernetes, Airflow, S3) and the Versioned Template Library concept

AirPy remains a technically strong alternative with the best results in several categories, in particular runtime performance, operational integration, internal expertise and Greenbook compliance. It is not recommended as the primary solution because it would require developing and maintaining a custom extraction framework in Airflow and, for Kafka and Elasticsearch, a second tool. AirPy remains a viable fallback if the validation items below cannot be fulfilled.

The recommendation is subject to the following validation items:

  • CyberArk integration and password rotation validated in a Proof of Concept with credentials supplied by Airflow for each run
  • The pod lifecycle solution (wrapper or NiFi Stateless runtime) validated, including the propagation of the exit code to Airflow
  • The Parquet, Kafka, Elasticsearch and AWS processors confirmed as available in the MiNiFi Java distribution, including the use of the internal S3-compatible storage
  • Runtime verified for larger volumes and for loading into target databases, including Teradata
  • Greenbook compliance of MiNiFi confirmed
  • Effort estimate for MiNiFi (environment setup, upskilling, migration) prepared

Risks and Mitigations

Risk Mitigation
No internal NiFi or MiNiFi expertise Structured training of the Platform Squad, reusable templates and documentation. Squads maintain only the YAML configuration.
MiNiFi Java is a continuously running agent without a documented run-once mode Implement a wrapper in the pod (start the flow, wait for completion, stop the agent, return the exit code) or evaluate the NiFi Stateless runtime. Validate in the Proof of Concept.
CyberArk integration and password rotation not yet validated Validate in a Proof of Concept with credentials supplied by Airflow for each run. Use Kubernetes Secrets with restricted RBAC.
Custom code remains in the templates (watermark logic, YAML translation, MiNiFi Toolkit conversion) Implement it once in the Versioned Template Library and validate the configuration in pull requests.
Required processors missing in the MiNiFi Java distribution Verify the distribution early and build the image with the required NAR bundles.
Insufficient performance for very large-volume flows or for loading into Teradata Scale horizontally with one pod per load, use bulk loading options for the largest flows and verify the performance in the Proof of Concept.
Lower adoption of MiNiFi in the industry and weaker documentation Rely on the Apache NiFi community and release line; define clear responsibilities for the platform and the templates.

Conclusion

MiNiFi provides the best balance of functional coverage, ready-made components, CI/CD and target architecture fit, and it allows all source types, including Kafka and Elasticsearch, to be handled with a single tool.

AirPy remains a technically strong alternative and a fallback option. NiFi remains a technically strong option, particularly for streaming, but the MiNiFi deployment model offers the same processors with a simpler CI/CD and operating model. PowerCenter remains a stable short-term alternative with low adoption risk, but its licensing model, product lifecycle and limited strategic alignment reduce its suitability as the future target solution. Meltano was excluded after the Proof of Concept because of its runtime.

The recommendation is therefore to adopt Apache MiNiFi (Java agent) run in Kubernetes and started from Airflow as the standard extraction tool, subject to successful validation of the items listed in the Recommendation.
