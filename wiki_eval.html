1. Development and Adoption Complexity

Category Description

This category evaluates the effort required to introduce, operate, maintain, and further develop the solution within KB.

It focuses on long-term sustainability, organizational readiness, migration effort, and the complexity of implementing new data extraction pipelines.

  • Maintenance Complexity
    Complexity of operating, monitoring, troubleshooting, and maintaining the solution throughout its lifecycle.
  • Upskilling Effort
    Effort required for development, support, and operations teams to acquire the necessary skills and achieve productive use of the solution.
  • Licensing and Upgrade Cost
    Cost and effort associated with licensing, vendor support, platform upgrades, and lifecycle management.
  • Environment Setup Complexity
    Complexity of introducing and operationalizing the solution within KB, including infrastructure, networking, security, governance, and operational readiness.
  • Migration Complexity (Informatica Assets)
    Complexity of migrating existing extraction workloads currently maintained by Informatica teams using a lift-and-shift approach.
  • Migration Complexity (Adoki Assets)
    Complexity of migrating existing extraction workloads currently maintained by Adoki teams using a lift-and-shift approach.
  • New Source Extraction Development Complexity
    Complexity of implementing and deploying a new source-to-Parquet extraction pipeline according to the target architecture standards.

9. Evaluation Summary and Recommendation

Evaluation Summary

Several alternatives for generating Parquet datasets from source systems were evaluated across the following dimensions:

  • Development and adoption complexity
  • Implementation and migration effort
  • Functional capabilities
  • Data Mesh alignment
  • Target architecture alignment
  • Security and governance
  • Operational capabilities
  • Proof of Concept results

Following the initial assessment, the Preparing Extracts at Source (PNJ) and Adoki Offloader alternatives were excluded from further consideration. These options introduced significant disadvantages in terms of operational complexity, long-term sustainability, contractual or platform dependencies, and overall cost.

The final comparison therefore focused on the following alternatives:

  • Airflow + Python (AirPy)
  • Apache NiFi
  • Informatica PowerCenter (Infa)

Key Findings

Airflow + Python (AirPy)

AirPy achieved strong results across most evaluation categories and demonstrated the best overall balance between flexibility, maintainability, architectural alignment, automation, and long-term viability.

Key strengths:

  • No licensing costs
  • Reuse of the existing Airflow platform and operational ecosystem
  • Strong CI/CD and Git integration
  • Simple automation and generation of new extraction flows using templates
  • Good alignment with the target cloud architecture
  • Strong operational capabilities, including monitoring, retry mechanisms, alerting, autorestarts, and SLA handling
  • Good alignment with Data Mesh principles and squad ownership
  • Potential reuse across other entities and data integration use cases

Key limitations:

  • A higher initial investment is required to build the reusable extraction framework
  • Incremental extraction logic must be implemented as part of the common framework
  • The solution depends on maintaining sufficient internal expertise and ownership
  • Python-based processing may not provide sufficient performance for all future high-volume workloads
  • In addition to the Société Générale on-premises Airflow platform, the solution would require an Airflow runtime within the KB on-premises environment. The preferred option is to deploy a dedicated KB worker connected to the Société Générale Airflow platform through CeleryExecutor. However, this model may be subject to security restrictions on the Société Générale side. If the required cross-environment connectivity is not approved, a standalone, fully operational Airflow deployment within the KB environment would be required.

Apache NiFi

NiFi demonstrated strong technical capabilities and achieved the best processing performance during the Proof of Concept.

Key strengths:

  • Best runtime performance among the evaluated alternatives
  • Native support for streaming workloads and Kafka integration
  • Native support for incremental processing
  • No licensing costs

Key limitations:

  • More complex CI/CD integration and environment promotion
  • More challenging automated flow generation
  • More complex governance, version management, and object lifecycle
  • Complicated integration with Airflow orchestration
  • Higher adoption and training effort across squads
  • More complex integration with CyberArk and password rotation

Although NiFi is technically capable and demonstrated the best performance, it introduces additional operational, integration, and governance complexity without delivering proportional benefits for the evaluated batch-oriented source-to-Parquet use case.

Informatica PowerCenter

PowerCenter remains a mature and proven enterprise platform with significant internal adoption, existing expertise, and established operational processes.

Key strengths:

  • Existing know-how and operational experience within KB
  • Established integration with existing operational and security processes
  • Stable and proven operational model
  • Low adoption risk for existing Informatica teams
  • Natural separation of configuration and implementation ownership

Key limitations:

  • Additional licensing and lifecycle costs
  • Lowest performance observed during the Proof of Concept
  • Reduced flexibility for automated flow generation at scale
  • Limited support for Parquet generation without additional transformations
  • Limited long-term strategic outlook due to the product lifecycle
  • Lower alignment with the target cloud architecture

PowerCenter presents the lowest transformation and adoption risk, but it also provides the least strategic value for the future target architecture and retains dependency on a licensed platform with a limited lifecycle.

Cost and Implementation Effort

The total estimated implementation and migration effort is dominated by migration testing, which is broadly comparable across all shortlisted alternatives. The main differences are in the initial environment setup and squad upskilling effort.

Recommendation

Recommended option: Airflow + Python (AirPy)

Based on the overall evaluation, AirPy is recommended as the target solution for future source-system-to-Parquet extraction workloads.

The recommendation is primarily driven by:

  • Strong alignment with the target architecture
  • Good fit with Data Mesh principles and squad ownership
  • Reuse of the existing Airflow ecosystem
  • No additional licensing costs
  • Strong CI/CD, Git, and automation capabilities
  • Simple generation and maintenance of a large number of extraction pipelines
  • Strong operational capabilities, including retry mechanisms, autorestarts, monitoring, and SLA integration
  • Good performance validated during the Proof of Concept
  • Long-term strategic viability and reuse potential

AirPy requires the development of a common framework for incremental loading, watermark management, schema validation, and Parquet generation. This is considered a one-time enablement investment that can be reused across migrated and newly onboarded extraction workloads.

The proposed solution also separates orchestration from the processing engine. Airflow remains responsible for orchestration, scheduling, monitoring, retries, and governance, while the most appropriate processing engine can be selected for individual extraction flows.

Risks and Mitigations

Risk Mitigation
Missing native support for incremental extraction logic Deliver a shared framework for watermark management, checkpoint overrides, and incremental processing as part of the initial implementation.
Dependency on internal know-how Establish common development standards, reusable templates, comprehensive documentation, structured training, and clear framework ownership.
Open-source support model Leverage existing platform ownership, internal support processes, and community-supported components. Define clear responsibilities for platform operation and framework maintenance.
Higher initial implementation effort Treat framework development as a one-time investment that will be reused across future extraction workloads and reduce subsequent onboarding, maintenance, and licensing costs.
Insufficient performance for very large-volume or computationally demanding extraction flows Integrate Apache Spark as an optional processing engine for selected high-volume flows while retaining Airflow orchestration, the common configuration framework, and the established governance model.
Future growth of data volumes may increase processing times Scale the Airflow execution infrastructure horizontally and offload resource-intensive processing to Apache Spark where appropriate.

The performance risk is considered manageable. The Proof of Concept demonstrated that AirPy provides sufficient performance for the evaluated workload. If selected extraction flows exceed the practical limits of Python-based processing in the future, Apache Spark can be used as a specialized processing engine for those flows.

This approach allows the processing engine to evolve independently of the orchestration and governance layers. Selected workloads can therefore be moved to Spark-based execution without redesigning the overall solution, changing the Airflow orchestration model, or replacing the common CI/CD and configuration framework.

Conclusion

AirPy provides the best overall balance of performance, cost, automation, operational capabilities, architectural alignment, and long-term strategic value.

NiFi remains a technically strong option, particularly for streaming and Kafka-oriented use cases, but introduces unnecessary complexity for the evaluated batch-oriented source-to-Parquet scenario. PowerCenter remains a stable short-term alternative with low adoption risk, but its licensing model, performance, product lifecycle, and limited strategic alignment reduce its suitability as the future target solution.

The recommendation is therefore to adopt Airflow + Python as the standard orchestration and extraction framework, with Apache Spark available as an optional processing engine for selected high-volume or computationally demanding flows.

10. Open Points

  • Generation of Parquet datasets from Kafka streams

    The approach for processing Kafka streams has not yet been finalized. The preferred option to be evaluated is the use of a Kafka Connect Sink Connector, which would read selected Kafka topics based on configuration and write the data directly to the target storage in Parquet format.

    The availability of a suitable connector for the target storage, Parquet support, schema handling, partitioning, file rotation, and operational ownership must be verified.

  • Processing of text-based files

    It has not yet been confirmed whether text-based files, such as XML, CSV, or JSON, will be processed through the ingest tool.

    The current assumption is that the ingest tool will not be responsible for converting these files into Parquet format. This assumption, including the expected processing path and ownership of these file-based inputs, must be validated.
