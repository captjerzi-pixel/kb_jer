Open Point

For the 113 Informatica workflows that rely on source data availability checks, it will likely not be possible to integrate a direct query from Gen2 Orchestration to the source system's internal knowledge base (KB) to verify data availability. As a result, the on-premises SOGE Airflow environment may not be able to determine precisely when parquet file generation should be triggered.


Concept of Ingest tool for DataMesh


A) Centralized Parameterized Ingest Tool

The centralized Ingest Tool has access to all ingest configurations and automatically executes all defined ingestion flows based on these configurations.

Advantages

  • All ingestion logic is maintained in a single place.
  • Functional changes only need to be implemented in the central tool.
  • No generation or maintenance of individual flow implementations is required.
  • Provides centralized governance and operational control.

Disadvantages

  • Ownership and operational responsibility cannot be clearly assigned to individual Business Unit squads.
  • Dataset-specific issues (e.g., an invalid Parquet schema) must be investigated and resolved by the Ingest Tool squad.
  • Business squads cannot independently trigger or rerun their own flows when required.
  • A failure or outage of the central tool may impact all ingestion flows.
  • Creates a strong operational dependency on a single component.


B1) Ingest Template Generator

The generator creates a complete ingestion flow as a standalone process based on the configuration. The generated flow is fully self-contained and does not require access to metadata or any shared runtime layer during execution.


Advantages

  • Each flow has a clearly defined owner.
  • Flows are fully independent and can run in parallel.
  • A failure in one flow does not affect other flows.
  • Operational responsibility can be delegated to the corresponding squad.
  • Flow behavior is controlled through metadata configuration, in line with Data Mesh principles.

Disadvantages

  • The same functionality is duplicated across all generated flows.
  • Each flow contains its own copy of the ingestion logic.
  • Adding new functionality or fixing defects requires regeneration and redeployment of all flows.
  • Changes to shared logic must be propagated to all generated instances.
  • The concept requires a mechanism for bulk regeneration and redeployment of all flows.

B2)  Versioned Template Library


The Templates Library provides versioned ingest flow templates for different processing patterns, such as full, delta, or kafka ingestion. Each template contains the complete ingestion implementation, while squad-specific behavior is configured through referenced YAML files. A squad selects the appropriate template and deploys a copy of it, together with its YAML configuration, into its own Git repository. From that point onward, the squad owns the resulting flow, including its deployment, operation, and decision on when to upgrade to a newer template version.

The Ingest Tool Owner Squad maintains only the central templates and, when an important update such as a security patch is released, requests all squads to independently adopt, test, and deploy the updated template.




Advantages

  • Each flow is self-contained, independently deployable, and owned by the corresponding squad.
  • Squads can decide when to adopt a new template version.
  • Failures and upgrades of one flow do not directly affect other flows.
  • Different template versions can coexist, enabling gradual migration.
  • Security fixes and functional enhancements can be distributed as versioned template releases.
  • Pull-request validation can verify compatibility between the selected template version and its YAML configuration.
  • Restricted customization (just YAML config path?) helps preserve standardized behavior across squads.
  • Squads can select a template appropriate for a specific ingestion use case, such as full, delta, or Spark processing.

Disadvantages

  • Multiple template types and versions must be developed, tested, documented, and supported.
  • A central inventory of flows, owners, and deployed template versions is required.
  • Security and critical defect fixes depend on squads performing the requested upgrade.
  • A lifecycle policy is required to prevent unsupported versions from remaining in production indefinitely.
  • Validation must reflect the exact configuration schema supported by each template version.
  • A thick flow can hide the execution details of individual objects behind a single processing cycle.
  • Full and delta processing may require separate flows, increasing the total number of deployed flows.
  • Common enhancements may need to be implemented separately across several template types.

C) Ingest Framework with Generated Thin Clients

The generator creates only a thin client for each metadata-driven flow. The client contains minimal logic and primarily serves as an independently owned execution unit. During runtime, the client loads its configuration and passes it to a shared framework that performs the actual ingestion processing and Parquet generation.

This approach combines decentralized flow ownership with centralized implementation of ingestion logic, providing a balance between operational autonomy and maintainability.


Advantages

  • Each flow has a clearly defined owner and operational responsibility.
  • Flows can run independently and in parallel.
  • Ingestion and Parquet generation logic is centralized in a shared framework.
  • Framework enhancements can be deployed centrally without regenerating all flows.
  • Minimizes duplication of common functionality.
  • Supports a Data Mesh ownership model.

Disadvantages

  • Introduces a dependency on a shared framework.
  • A defect in the framework may impact multiple flows simultaneously.
  • Compatibility between the framework and generated clients must be managed.
  • The shared framework becomes an additional component that must be versioned, tested, and operated.

Selected Target Solution

Based on the evaluation of the proposed concepts and the target operating model for Data Mesh, the Versioned Template Library (B2) has been selected as the target solution.

This model provides a balanced combination of standardization and squad autonomy. The Ingest Tool Owner Squad is responsible for developing, maintaining, and versioning standardized ingestion templates, while individual Business Unit squads own the resulting flows, including deployment, operations, and upgrade planning.

Compared to a fully centralized solution, B2 better supports Data Mesh principles by assigning clear ownership and operational responsibility to data-producing teams. Unlike the fully generated approach (B1), it enables controlled reuse through versioned templates and allows squads to adopt new functionality, enhancements, and security fixes according to their own release schedules.

The approach introduces additional governance requirements, particularly around template lifecycle management, version inventory, and upgrade policies. However, these challenges are considered manageable and are outweighed by the benefits of decentralized ownership, operational independence, controlled standardization, and gradual evolution of the platform.

As a result, the Versioned Template Library (B2) has been selected as the target architecture for both the migration of existing ingestion workloads and future Data Mesh-based ingestion development.
